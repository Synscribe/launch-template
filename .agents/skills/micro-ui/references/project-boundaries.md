# Project boundaries

## Sources

- Tokens and reduced-motion baseline: `src/app/globals.css`
- OG image: `src/app/opengraph-image.tsx`
- Use-case content: `src/content/use-cases/*.json`
- Stable visual IDs: `src/lib/visuals.ts`
- Shared visual resolver and source map: `src/components/visuals/project-visual.tsx`
- Shared React visuals: `src/components/visuals`
- Use-case placement wrapper: `src/app/uses/[slug]/_components/use-case-visual.tsx`
- Use-case local files: `public/media/uses`
- Motion kit, once copied in: `src/components/visuals/visuals/_kit.tsx` and `brand.ts`
- Gated visual inventory: `src/app/dev/visuals/page.tsx`
- Gated launch gallery: `src/app/dev/launch-assets`
- Launch exporter: `scripts/launch-assets.mjs`
- Homepage-only composition: `src/app/(marketing)/_components`
- Launch requirements and status: `docs/launch/checklist.json`
- Generated readable checklist: `docs/launch/checklist.md`

## Placement

- Keep a one-route visual in that route's `_components` folder.
- Promote only after a second real consumer. The shared project visual resolver is promoted code:
  use cases, the gated inventory, and launch assets all consume it.
- Keep use-case JSON limited to content and one `visualId` per hero/capability. Component names,
  file paths, props, and layout do not belong in JSON.
- Add allowed IDs to `VISUAL_IDS`, then populate the exhaustive
  `Record<VisualId, VisualSource>` in `project-visual.tsx` so TypeScript catches missing sources.
- Use `kind: "component"` for React, including an isolated Client Component when justified. Use
  `kind: "image"` for an approved project-owned file with intentional alt text.
- Keep route-specific figure sizing and copy with the route. `UseCaseVisual` remains a thin
  placement wrapper; it does not own a second source map.
- Prepare local images for every real placement and inspect the crop. Do not depend on an
  arbitrary source crop.
- Keep the default OG implementation generated by Next unless the project explicitly needs
  uploaded/static social assets.

## Gated review workspace

- `/dev`, `/dev/visuals`, and `/dev/launch-assets` exist only when the server receives the exact
  `VISUAL_REVIEW_ENABLED=true` allow value.
- `.env.example` enables the workspace for copied local configuration. Do not set the value on a
  public deployment.
- The routes stay out of navigation and sitemap, carry noindex metadata, and remain disallowed in
  production robots policy.
- The launch exporter supplies the allow value only to its temporary local `next start` process.

## Motion kit

- `framer-motion` is the one approved animation dependency. It exists for looping capability
  visuals; it is not the default mechanism for page-level motion.
- Copy `references/examples/_kit.tsx` and `brand.ts` into
  `src/components/visuals/visuals/` on first real use, and extend that copy rather than starting a
  second kit.
- Keep animation for a non-kit route feature in that route's `_components` folder or route CSS
  module, and prefer CSS transitions and keyframes there.
- Preserve Server Components by default. Isolate only the looping or interactive fragment in its
  own `*.client.tsx` module when client state is necessary.
- Do not serialize animation configuration into content JSON.
- Do not add a second motion or graphics dependency.

## Design tokens

Use the current semantic palette rather than copying literal colors from another product:

- canvas/paper for surfaces;
- ink/ink-muted for hierarchy;
- signal for the primary accent;
- mint/mint-strong for completion and supporting emphasis;
- night for dark stages.

Read the actual values before rendering an image because clients may replace every token.

## Verification

Relevant checklist IDs are `BRAND-01`, `BRAND-02`, `SOCIAL-01`, `PERF-01`, `PERF-02`, `A11Y-01`,
and `IMAGE-01`. Do not duplicate their requirements here. Verify the rendered asset or page, then
update the matching status in the canonical JSON.
